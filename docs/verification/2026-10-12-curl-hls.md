# curl HLS 下载验证

日期：2026-10-12。HLS 下载从 N_m3u8DL-RE 改为“TypeScript 规划 + 每个任务一个 curl 进程并行下载分片 + FFmpeg 读取本地播放列表合并”，设计见 [ADR 0007](../decisions/0007-video-downloads.md#hlscurl-并行下载与本地合并2026-10-12-修订)。

## 起因排查

用户反馈的失败任务停在 N_m3u8DL-RE 读取播放列表这一步，返回 403。本次经用户授权访问了该真实来源，但只在命令行看状态码、响应头和 m3u8 文本，没有打开、预览或播放任何图片和视频。

| 客户端（同一链接、同一本地代理）                                 | 结果                                    |
| ---------------------------------------------------------------- | --------------------------------------- |
| curl，Origin + Referer + User-Agent                              | 200                                     |
| curl，按 N_m3u8DL-RE 实际发送的请求头和顺序原样复刻              | 200                                     |
| .NET 10 HttpClient / 强制 HTTP/2 / .NET Framework，请求头同 curl | 403（Cloudflare “Attention Required!”） |
| N_m3u8DL-RE 0.5.1，直连与代理，补齐 Accept 等请求头              | 403                                     |
| Windows 自带 curl（只支持 SChannel）                             | 200                                     |

实际发出的请求头是用本机回显服务抓到的。结论：拦截依据是 .NET 客户端本身，与请求头无关，N_m3u8DL-RE 的参数无法绕开。

改用 curl 后又发现一处差异：资源解析会把请求头名转成小写。随包 curl 发送小写 `user-agent` 时，同一 CDN 返回 403；改成 `User-Agent` 后返回 200。现在交给 curl 前统一规范请求头名的大小写。

  - AES-128 加密 HLS：curl 下载密钥和分片，FFmpeg 在本地解密并合并，产物有视频、音频，时长超过 11 秒；

调试中发现，curl 的 `--write-out` 写入管道时会被 C 运行时缓冲，分片结果要到进程结束才一起出现，进度和暂停时的记录都会受影响。现在改为通过 `%{stderr}` 输出，“暂停后继续”用例覆盖了这一点。

## 真实来源（仅命令行）

使用随包的 curl 8.22.0 和精简 FFmpeg，下载原本失败的那条链接，没有打开任何画面：

- 直连成功，没有切换代理。共 1777 个分片，8.8 秒内完成 83 个，速度约 9 MB/s，估算总大小约 1.35 GB。
- 下载到 4% 时主动取消，`state.json` 记录了已完成的分片。
- 截取前 81 个连续分片生成本地播放列表，用随包精简 FFmpeg 合并：输出有视频和音频，时长 324 秒，与播放列表一致。
- 临时目录 `.tmp/real-hls` 已删除，没有残留 curl 进程。

## 大小估算与合并修复（同日第三轮）

大小估算改为“按轨道、按时长”推算，加上跨度下载顺序和声明码率初值，详见 [ADR 0007](../decisions/0007-video-downloads.md#hls-大小估算)。

- `pnpm test tests/download-hls.test.ts`：41 项通过。用合成影片（片头片尾低码率、正片波动，外加小而稳定的音频分片）模拟：下载到 5% 时，新算法的估算误差小于 5%；同样位置下，旧的“分片平均值 × 分片数”加顺序下载误差超过 30%。5 万个分片的排序在 200 ms 内完成。
- 让 `JAVM_CURL`、`JAVM_FFMPEG` 指向随包工具，运行 `tests/download-engine.integration.test.ts` 全部 29 项：全部通过（筛选词 `HLS` 命中了套件名，因此实际执行了整个文件，包括既有的 HTTP 用例）。
- 这一轮发现并修复了一个从第一轮就存在的问题：主播放列表含 fMP4 视频和独立 TS 音频时，合并失败并报 “Non-monotonic DTS”。手动复现确认，单独的视频和单独的音频都能正常封装，根因是 `-xerror` 把 FFmpeg 平时会自动修正的重复时间戳升级为致命错误。去掉后，同样的输入合并为 12.03 秒、含视频和音频的 MP4，完整解码没有错误。完整版 FFmpeg 和随包精简版的表现一致。
- 没有对真实来源测量估算误差：真实总大小需要完整下载约 1.35 GB，或对全部分片发 HEAD 请求，这两种都不在本次范围内。

## 并发限制、刮削诊断与界面文案（同日第八轮）

第七轮的包在用户电脑上已合并成功：723 个分片的 PNG 头均为 70 字节，跳过后 FFmpeg 正常退出。用户随后反馈第二个视频下载不动、刮削失败，以及搜索界面的文案太啰嗦。

- 下载不动：见 ADR 0007“源站并发限制与停滞”。测试服务器新增 `/limited/` 路径，同一时间只服务 1 个请求、其余挂起。使用随包 curl 时，并发逐轮降低，最终下载完成并合并成功。单元测试覆盖停滞后减半并发和看门狗期间仍可取消。
- 刮削：用户日志显示三次搜索各约 11 秒后返回 404。本机用随包 MetaTube 搜索 MDBK-418，直连、`http://`、`socks5://`、`socks5h://` 代理均返回 200，FANZA 有结果；可见番号可查、代理写法不是原因，问题在用户电脑的 MetaTube 访问资料来源这一环。之前 MetaTube 自己的输出没有进入应用日志，现在把每次查询的各来源结果汇总行（来源、耗时、错误，不含标题）和错误行写入日志，并记录是否走代理（不记录代理地址），等待用户电脑上的日志进一步定位。
- 界面：移除搜索框上方的“正在匹配：… 选择正确资料后点击‘采用并刮削’”；出错时只显示一条错误提示，不再追加“影片资料未能加载，请重试。”；404 文案改为“没有找到资料，请检查番号或网络代理。”，没有结果时显示“没有找到匹配结果。”
