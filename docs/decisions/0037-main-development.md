# ADR 0037：统一在 main 开发与发布

- 日期：2026-10-15
- 依据：用户要求先推送异常反馈功能到 dev，再合并 main、移除 dev，并将后续开发和相关流程迁移到 main。

## 分支

异常反馈功能先以 `ee4e82e` 提交并推送 dev，再以保留双方历史的合并提交并入 main。旧 main 独有的 Windows 发布工作流依赖已废弃的工程脚本，因此保留其历史，不恢复该工作流；继续使用当前跨平台发布方案。

确认远端 main 包含 dev 的全部提交后，删除远端与本地 dev。仓库默认分支和本地开发分支统一为 main，不重写已有历史，不调整其他分支和未合并 PR。早期 ADR 与验证记录中的 dev 表示当时状态，保持历史原文。

## 工作流

- `third-party.yml`：main 上相关构建配方变更触发指纹检查，也可手动执行；相同配方继续复用已有组件 Release。仅切换分支不会改变组件指纹。
- `release-alpha.yml`：沿用文件名，统一承载正式版、Beta 和 Alpha 的跨平台发布；所有应用标签必须属于 `origin/main`。
- 工程检查、跨平台检查、更新隔离验收和签名密钥维护：在 main 手动触发。移除两条一次性初始化分支的 push 入口，密钥维护不随日常提交自动执行。
- 继续保留安装包、便携包、更新包与签名、文件清单及校验信息。只有正式应用版本标记为 Latest，组件发布不得占用 Latest。

## 发布步骤

1. 同步 package.json、neutralino.config.json、README.md 与 CHANGELOG.md 的版本和说明。
2. 按发布范围完成检查和测试，提交并推送 main；如组件配方变化，等待对应组件发布完成。
3. 创建并推送唯一的 `v版本号` 标签。当前补丁版本为 `v1.0.6`。
4. 等待 Windows、macOS arm64/x64 与 Linux x64 构建和隔离验证通过。发布任务汇总附件，上传草稿并逐一下载比对 SHA-256 后才公开。
5. 再核对公开 Release、更新清单、下载附件和版本来源。公开标签及附件不可覆盖。
